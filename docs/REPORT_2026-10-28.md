## 3. 任务 B：端侧骨架

### 3.1 core/（大家共用）

- `types.h`：深度帧（帧号、单调时钟时间戳、内参版本）、9×6 栅格（0/1/2，每格诊断：高度带点数、地面点数、看到地面的 10 cm 小块数）、地面估计、各阶段像素数。行号约定与 `frame_converter.py` 一致：row 0 最远。
- `modules.h`：按视觉方案第 9 节命名的接口：SensorAdapter、Registration、GroundPose、GeometryGrid、RGBInstance、SpatialLMService、EvidenceFusion、OutputAdapter / TactileEncoder。`inference.h`：InferenceBackend（鸿蒙 MindSpore Lite、安卓 ONNX Runtime）和 LanguageModel（llama.cpp）。未实现的只有接口，没有假实现。
- `tactile.h`：旧板编码。9×6 放进 10×9 的最近 6 行，其余 4 行全平。
  - 状态 2 用 `UnknownCellPolicy` 显式传入，没有默认值；数值 0 非法，防止零初始化时悄悄选中一种。
  - 左右镜像、ROT180 都是显式参数，默认沿用现有行为（都为 true）。
- `config/lingtouch_defaults.conf`：全部门槛的唯一来源，编译时原样嵌入，两个平台共用。`tactile.unknown_cell_policy` 留空，注明“待 Hsinlung 定”。
- `engine.h`：给外壳的门面，包括启动表、IN 响应、按批收包、后台线程算栅格（只保留最新一帧）、编码、存帧和核对帧文件。没有帧或没有内参时拒绝编码。
- `report_json.h`：两端共用的栅格/统计 JSON 和栅格摘要。

### 3.2 perception/native/（视觉同学）

- **启动表**：由 `tools/gen_startup_sequence.py` 从 `startup_sequence.json` 生成，不手抄。共 41 条控制请求、2 次切换接口、1 次挂等时传输。0xa700 之后的 270 ms 等待不在 JSON 里，由脚本按 REPORT 第 9 步加上。
- **执行顺序**：JSON 的第 0 步（GET_CUR 0xcb00）排在“接口 0 设 alt 0”之前。执行时先 claim 接口 0，再严格按表走。
- **拆帧器**：与 `independent_proof.py` 的 `packet()/finish()` 逻辑一致，处理 UVC 头、FID 翻转、EOF、ERR、空包、超长。
- **标定解码**：无 schema。字段含义和依据见 §6。
- **几何**：
  - 去畸变查表；
  - 依次过滤：无效值（0、恰为 1、<100 mm、>5 m、超出畸变可逆范围）→ 疑似相位绕回的孤立近点 → 边缘飞点（默认偏松）；
  - 反投影：光轴 Z / 径向可切换（`depth.meaning`），去畸变可开关（`depth.undistort`），深度图镜像可开关（`depth.image_mirrored`）；
  - 地面拟合：RANSAC + 最小二乘（Jacobi）。质量检查包括内点数、前向铺开长度，以及“低于平面的点占比”（防止把桌面当地面），失败时整张为 2；
  - 0/1/2：先按 10 cm 小块取整再推出格子；1 优先于 0；0 要求 16 个小块都有地面点且高度带内无点（缺几块、带内允许几个点都是参数）。
- **平面检查**：中央区域对四种假设（Z/径向 × 去/不去畸变）各做最小二乘平面，比较残差。
- **确定性**：两个平台要对同一帧算出相同结果，所以 `-ffp-contract=off`、不用 fast-math，判决只用加减乘除和 sqrt，随机数用自带的 SplitMix64。
- **cs30_libusb**（安卓用，可选目标）：
  - 用 `LIBUSB_OPTION_NO_DEVICE_DISCOVERY` + `libusb_wrap_sys_device` 包住 fd，claim 时自动 detach 内核驱动；
  - 挂 10 个传输，每个 32 个微帧 × 3072 字节，超时 5000 ms；控制请求超时 15 s；
  - 停流顺序：取消并排空（每轮重新取消）→ 接口 1 设 alt 0 → 接口 0 设 alt 0 → release；
  - 停流时若还有传输没回来，不释放缓冲，并拒绝重开；另有 `reset_device()`。
- **third_party/libusb**：上游 1.0.29（LGPL-2.1）Linux/Android 后端原样摘取，压缩包 SHA-256 记在 `README.lingtouch.md`。编成独立的 `libusb-1.0.so`，不静态链接。

### 3.3 agent/native/（对话 agent 同学）

只有接口：语音识别/合成（计划用 sherpa-onnx）和 agent。语言模型接口放在 core，因为 SpatialLM 和 agent 共用。

### 3.4 apps/android/（交互同学）

Kotlin，不依赖 AndroidX。AGP 8.7.3 / Kotlin 2.0.21 / Gradle 8.11.1，minSdk 29、targetSdk 35，只编 arm64-v8a。

- MainActivity 的流程：申请 CAMERA（安卓 9 起 UVC 授权需要）→ USB 授权（PendingIntent 显式包名 + FLAG_MUTABLE，接收器 NOT_EXPORTED）→ 后台线程开流 → 每 200 ms 刷新。
- 栅格每行有读屏文字。没连设备显示“未连接”，帧率只用实测帧数算。状态 2 不预选、必须手选。
- 另有：持续发送、平面检查、存帧/核对帧文件、复位相机。
- StreamService 是 connectedDevice 前台服务，开流期间持有 `PARTIAL_WAKE_LOCK`。HandleLink 的 BLE 流程与比赛版相同，FFE3 订阅成功后才允许写帧。

### 3.5 apps/harmony/（交互同学）

ArkTS Stage 模型，`compatibleSdkVersion = targetSdkVersion = 5.1.0(18)`。

- **主路径**：usbManager 执行启动表，接口 1 切到 alt 1 后立刻挂 10 个 `usbSubmitTransfer`。每个回调把 32 个微帧打成一批，调一次 `pushIsoTransfer`，不是每包一次跨层调用。
- **备选路径**：`getFileDescriptor` → `openFd` → native libusb。CMake 开关 `LINGTOUCH_HARMONY_LIBUSB` 可以关掉。
- **BLE**：取自比赛版，改成回调对象，并且不跳过相同帧（后台持续发送测试要看到每次刷新）。
- **后台保活**：长时任务 bluetoothInteraction + location，module.json5 里已声明。
- 界面功能与安卓相同。

## 6. 标定与深度含义（实测、计算、推断分开）

- **实测（读文件）**：两份 blob 都是 763 字节，只差 5 个字节，全在字段 1 的 4 个 float 里。blob 0 字段 1 = 364.875 / 364.778 / 324.416 / 231.051；blob 1 正好是一半（浮点指数减一）。字段 2 = −0.316446、0.140359、−0.000302、−0.000482、−0.034901。字段 11 = `HV0130315L0294`。
- **推断**：字段 1 是 640×480 的深度内参 fx fy cx cy，字段 2 是 OpenCV 顺序的 k1 k2 p1 p2 k3；blob 1 对应 320×240；字段 15–17 像是 RGB 内参与畸变（931.03 / 930.71 / 976.96 / 554.82…）、RGB←深度的旋转（接近单位阵）和平移（约 −43.9，推断单位毫米）。代码里内参版本号带 `:inferred`。
- **计算**：按上述含义，横向视场约 100.2°，与规格书的约 100° 一致；纵向约 75.0°。径向畸变函数在未畸变半径约 1.40 处到顶，所以图像四角约 6.58% 的像素超出可逆范围。查表把这些像素标为无效，查表回投最大误差 1.1e−5 像素。
- **交接里“解不出就用规格书视场推临时内参”这一条没有实现。** 解码成功，用不上；而且这颗镜头桶形畸变很强，按 100° 推的针孔焦距约 268 px，比解出的 365 px 小约 26%，会比没有更误导。换真标定的入口是 `Engine::set_intrinsics`（或改解码）。
- **深度是光轴 Z 还是径向：未确认。** 材料里找不到依据。参考帧是近场数据，判断不了（四种假设残差都只有 4–5 mm，而且拟合到的“平面”离相机约 1 cm，没有意义）。合成测试表明平面检查能区分：
  - 正对墙时，对的假设残差 0.0–0.3 mm，含义错了 57–82 mm；
  - **但正对墙时光轴 Z 深度在整面墙上是常数，去不去畸变墙都一样平**，所以要判断去畸变，得斜着拍一个平面。俯仰 45° 看地面时，对的 0.2 mm，不去畸变 8.7–13.5 mm。
  - 据此把真机清单的平面检查写成两步。

## 7. 我改动或补充“Claude 判断的”地方及理由

1. **鸿蒙 API 16 → 18。** OpenHarmony usbManager 文档把 `usbSubmitTransfer` 等标为 18+，Hsinlung 已确认，交接文档也改了。
2. **核心“无平台依赖”与“核心用 libusb”的处理。** libusb 取流放在 `perception/native/cs30_libusb`，是单独的可选目标，只有安卓（以及鸿蒙备选路径、桌面 Linux 检查）链接；核心本身不依赖它。
3. **接口归属。** 语言模型接口放 core（SpatialLM 与 agent 共用），语音和 agent 接口放 `agent/native`。
4. **规格书临时内参没有实现**，理由见 §6。
5. **新增 `depth.undistort`、`depth.image_mirrored` 两个参数**，以及畸变不可逆像素标无效。片上是否去畸变、图像是否镜像都未确认。
6. **左右镜像做成显式参数，默认开**（Hsinlung 已同意）。
7. **地面拟合加了“低于平面的点占比”检查**（默认 >5% 就判失败）。没有它，桌面占多数时会把桌面当地面，宁可降级成 2。
8. **0 的规则里“高度带内无点”** 用 `grid.free_max_band_points = 0` 实现，可调。带内有点但不到 1 的门槛时，判 2。附带观察：默认参数下 5 cm 以内的扁平物体（地面容差 5 cm）会被当成地面点。
9. **真机清单第 1 条的方法改了。** 手机上不能跑厂家 SDK，做不到“同一次曝光哈希一致”，改为先后两次曝光比对（`compare_frames.py`，参考值用 REPORT 的中位数约 3 mm、P95 约 12 mm）。为此给两个 App 加了“保存当前帧”。
10. **第 3 条**加了栅格摘要和“核对帧文件”，电脑、安卓、鸿蒙三边可以直接比对。
11. **第 2 条**补了依据：OpenHarmony USB DDK 文档里 `OH_Usb_SendPipeRequest` 只写了中断和批量传输；按 Hsinlung 的要求加了备选路径 getFileDescriptor + libusb，与 usbSubmitTransfer 一起测。
12. **安卓前台服务外加 `PARTIAL_WAKE_LOCK`。** 只有前台服务时，息屏后 CPU 可能休眠，息屏 10 分钟那条测试就会失败。
13. **鸿蒙 HandleLink 不再跳过与上一帧相同的帧**（比赛版会跳过），否则静止场景下后台持续发送测试看不到刷新。
14. **没数据时不发帧。** 没有帧或没有内参时，`encode_legacy` 拒绝编码。地面拟合失败（降级、整张 2）时照常按状态 2 的策略编码。

## 8. 给 Hsinlung 的待办

- 按 [device_tests.md](device_tests.md) 测。最要紧的是两个平台能否收到帧，以及鸿蒙 `usbSubmitTransfer` 的实际表现。
- 定下状态 2 的触点表示，写进 `tactile.unknown_cell_policy`。
- 平面检查后，定 `depth.meaning`、`depth.undistort`；手摸后确认两个镜像开关。
- 合并后先运行一次迁移脚本（建议先 `-DryRun`）。
