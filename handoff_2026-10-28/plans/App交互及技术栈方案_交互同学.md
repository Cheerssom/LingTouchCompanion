## 本项目可采用的交互方式

| 方式 | 用途 |
| --- | --- |
| 语音指令 | 支持“读一下”“再说一遍”“停”等自然表达。 |
| 触摸与读屏 | 主要入口固定，控件名称清楚。 |
| 震动反馈 | 提示操作已接收、任务完成或需要注意。 |
| 音效 | 提示开始收音、拍摄完成等瞬时状态。 |

App 定位为设备管理、模式控制、导航与语音辅助中心。

保留已有的 uni-app + Vue 3 工程，以 Android 为首发平台，先完成真实 BLE GATT、无障碍语义和关键任务闭环；随后再分别完成 iOS 与 HarmonyOS 的设备能力适配和真机验收。

## 技术栈

| 方案 | 跨端路径 | 与现有项目关系 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- |
| A<br>uni-app + Vue 3 + TypeScript | Android/iOS 使用 App 构建路径；HarmonyOS 使用对应适配与原生扩展能力。 | 最大程度复用现有 Vue 页面和接口；把新增通信模块逐步改为 TypeScript。 | BLE、后台、TTS 与无障碍语义必须逐平台真机验证；不能把能打包等同于能用。 | 当前首选 |
| B<br>Flutter + Dart | Android/iOS 为官方支持路径；HarmonyOS 依赖独立适配生态与平台插件。 | 需重写已有 uni-app 前端，但长期可获得更统一的渲染与组件体系。 | 鸿蒙插件成熟度、三端原生桥接和迁移成本。 | 整体重构备选 |
| C<br>三端原生 | Kotlin/Compose、Swift/SwiftUI、ArkTS/ArkUI。 | 通信协议可共用，界面和平台能力分别实现。 | 三套客户端维护成本最高，需要稳定的多人分工。 | 资源充足时采用 |

推荐：前端继续采用 uni-app、Vue 3，并从新增模块开始使用 TypeScript；Android 为首个可验收平台。BLE 等关键能力使用 UTS 或平台原生插件封装，分别接 Kotlin、Swift 和 ArkTS。后端继续使用 Node.js + Express 只承载非实时服务；实时障碍到点阵的链路应尽量本地运行，不依赖云端。ESP32-S3 固件使用 ESP-IDF + C/C++，手机与设备使用 BLE GATT。

## 界面

底部三个入口：出行（全局、寻物，导航）、设备（配对、状态、诊断...）、我的（设置、帮助...）

| 界面 | 核心内容 | 关键操作与状态 |
| --- | --- | --- |
| 首次使用与无障碍引导 | 读屏提示、权限用途、设备实体按键说明。 | 逐项申请蓝牙、定位、相机和麦克风；拒绝后给出替代路径。 |
| 出行首页 | 设备连接、当前模式、电量、定位状态、一个主任务入口。 | 开始或停止任务；切换全局/寻物；状态用文字、语音和图标共同表达。 |
| 设备配对 | 发现的设备、设备标识、连接进度、失败原因。 | 扫描—选择—连接—服务发现—订阅—握手；支持忘记设备和自动重连。 |
| 任务进行中 | 目的地或寻物目标、剩余步骤、设备与感知状态。 | 暂停、重听、取消；断线时立即退出“正常运行”状态。 |
| 设备状态 | 电量、固件版本、连接质量、最后一次有效帧时间。 | 只展示真实采集值；无法取得时显示“未知”，不使用模拟健康结论。 |
| 诊断 | BLE、触觉刷新确认、感知端、权限和语音模块。 | 逐项测试并给出用户可执行的处理办法；高级延迟明细折叠显示。 |
| 设置与帮助 | 播报详细度、语速、震动、自动连接、隐私和教学。 | 提供触觉图案练习及安全使用说明；设置跨端保持一致。 |

## 流程

### 1 连接设备

打开设备页 → 解释为什么需要蓝牙权限 → 扫描附近设备 → 选择有明确名称或序列号的设备 → 建立 GATT 连接 → 发现指定服务与特征 → 订阅 Notify → 完成版本与能力握手 → 朗读“设备已连接，当前模式为全局模式”。任何一步失败都要说明失败位置，并提供重试或查看帮助。

### 2 全局

用户通过 App 或实体按键启动 → App 检查感知端、ESP32 与触觉点阵是否就绪 → 仅在收到有效状态确认后进入运行中 → 点阵持续刷新 → App 只播报转向、故障和必要提示 → 数据超时或 BLE 断开时立刻提示并将状态改为“触觉信息已暂停”。

### 3 寻物

用户说出或输入目标 → App 复述目标并确认（“正在寻找...”） → 感知端开始目标搜索 → 找到后由点阵表达相对位置，语音只补充必要说明 → 用户可说“再说一遍、换一个目标、停止”。未找到时应明确说“暂未识别到”，不能给出猜测位置。

## 项目现状

| 项目事实 | 当前情况 | 本方案处理 |
| --- | --- | --- |
| 系统链路 | 感知端生成空间信息，手机承担交互与触觉编码，ESP32-S3 接收 BLE 数据并驱动点阵。 | App 围绕连接、模式、状态、导航和语音展开，不把手机界面设计成主要避障界面。 |
| 现有前端 | 已有 uni-app + Vue 3 工程，包含出行、导航、设备和诊断页面。 | 优先渐进改造，避免无依据地整体换栈。 |
| BLE 状态 | 当前设备页和诊断页仍以延时与固定数值模拟，代码中保留真实连接待办。 | 第一开发任务应是真实扫描、连接、服务发现、订阅通知、断线恢复和错误态。 |
| 协议材料 | 材料中同时出现 15 字节点阵数据与 18 字节完整帧。 | 先冻结协议文档：帧头、模式、序号、15 字节载荷、校验、确认应答及超时。 |
| 安全边界 | 当前原型与材料不足以证明复杂城市道路上的全功能自主导航。 | 文案使用“辅助”“状态未知”“连接中断”，避免“绝对安全”“全部正常”等未经设备确认的承诺。 |

## BLE GATT 通信建议

| 对象 | 建议定义 | 说明 |
| --- | --- | --- |
| Device Info | 设备型号、固件版本、协议版本、能力位。 | 连接后先握手；协议版本不兼容时阻止进入运行态。 |
| Control Write | 启动/停止、模式、目标编号、震动测试。 | 写入命令携带序号；关键命令要求确认。 |
| Tactile Frame Write | 模式、序号、点阵载荷、校验。 | 材料中的 15/18 字节差异须先与固件统一；高频数据不要使用 JSON。 |
| Status Notify | 电量、当前模式、故障码、最后处理序号。 | 设备主动通知；App 将原始故障码翻译为可执行提示。 |
| Heartbeat | 双向心跳与超时阈值。 | 连续超时后退出运行态，不保留误导性的“正常”状态。 |

建议同时形成一份独立的协议表，至少写清服务 UUID、特征 UUID、读写权限、字节序、单位、范围、校验方式、确认应答、重试次数、超时和断线恢复。Android、iOS、HarmonyOS 与 ESP32 使用同一组协议测试向量。
